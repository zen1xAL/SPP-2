# Семантика стандартов HTTP и обработка ошибок (RFC 7231 / RFC 9110)

Данный документ содержит детальный анализ реализации семантики кодов состояния HTTP и унифицированного формата обработки ошибок в Лабораторной работе №3 в соответствии с современными стандартами RFC 7231 и RFC 9110.

---

## 1. Сводная матрица кодов состояния HTTP в проекте

| HTTP-код | Стандартное имя | Сценарий применения в Lab 3 | Возвращаемое тело |
| :---: | :--- | :--- | :--- |
| **`200`** | `OK` | Успешное чтение данных (`GET /tasks`, `GET /me`, `GET /sessions`), успешный вход (`POST /login`), обновление (`PUT /tasks/:id`), сброс пароля. | JSON с запрошенными данными |
| **`201`** | `Created` | Создание новой задачи (`POST /tasks`), регистрация нового пользователя (`POST /register`), прикрепление файла (`POST /tasks/:id/attachments`). | JSON созданной сущности + метаданные |
| **`204`** | `No Content` | Завершение сессии (`POST /logout`), отзыв активного подключения (`DELETE /sessions/:id`). | Пустое тело (0 байт) |
| **`400`** | `Bad Request` | Ошибки валидации формата входных данных (пустой заголовок задачи, невалидный email, пароль короче 6 символов, превышение размера файла > 5 МБ). | `{ error, code: "VALIDATION_ERROR", statusCode: 400 }` |
| **`401`** | `Unauthorized` | Отсутствие токена Bearer, недействительный/истекший JWT, сессия отозвана в БД (`is_revoked = true`), неверные учетные данные при входе. | `{ error, code: "UNAUTHORIZED", statusCode: 401 }` |
| **`403`** | `Forbidden` | Нарушение ролевой модели (RBAC): пользователь аутентифицирован (токен валиден), но его роль (`viewer`) не имеет прав на создание, редактирование или удаление задач. Либо попытка отозвать чужую сессию не-администратором. | `{ error, code: "FORBIDDEN", statusCode: 403 }` |
| **`404`** | `Not Found` | Запрашиваемая задача, файл вложения или идентификатор сессии не найдены в базе данных. | `{ error, code: "NOT_FOUND", statusCode: 404 }` |
| **`409`** | `Conflict` | Конфликт уникальности: попытка зарегистрировать пользователя с уже существующим в базе данных email. | `{ error, code: "EMAIL_ALREADY_EXISTS", statusCode: 409 }` |
| **`422`** | `Unprocessable Entity` | Семантические ошибки бизнес-логики: попытка использовать уже погашенный (`used_at IS NOT NULL`) или истекший одноразовый токен сброса пароля. | `{ error, code: "RESET_TOKEN_ALREADY_USED", statusCode: 422 }` |
| **`429`** | `Too Many Requests` | Срабатывание защиты от подбора паролей (Brute-Force Rate Limiting) при 5 неудачных попытках входа. Ответ сопровождается заголовком `Retry-After: 900`. | `{ error, code: "TOO_MANY_REQUESTS", statusCode: 429, retryAfterSeconds }` |
| **`500`** | `Internal Server Error` | Непредвиденные сбои времени выполнения (Uncaught Exception), сбои пула подключений к PostgreSQL. | `{ error: "Внутренняя ошибка сервера", code: "INTERNAL_SERVER_ERROR", statusCode: 500 }` |

## 2. Разбор ключевых семантических различий

### 2.1. 401 Unauthorized против 403 Forbidden
Это фундаментальное различие протокола HTTP:
- **`401 Unauthorized`** – проблема **аутентификации** («Кто вы?»). Запрос отклоняется, потому что клиент не предоставил учетные данные, токен поврежден, истек его 15-минутный срок жизни или сессия была принудительно отозвана.
- **`403 Forbidden`** – проблема **авторизации / прав доступа** («Я знаю, кто вы, но вам сюда нельзя»). Пользователь успешно аутентифицирован (например, вошел под учетной записью `viewer@taskflow.local`), но пытается совершить операцию модификации (`POST /api/tasks` или `DELETE /api/tasks/:id`). Сервер понимает запрос, но категорически отказывается его выполнять из-за ограничений роли.

### 2.2. 400 Bad Request против 422 Unprocessable Entity
- **`400 Bad Request`**: Синтаксическая или структурная ошибка запроса (отсутствует обязательное поле `email`, заголовок задачи состоит из одних пробелов, неверный JSON).
- **`422 Unprocessable Entity`**: Запрос синтаксически идеален (JSON валиден, типы полей корректны), но нарушена семантическая логика предметной области. Например, в эндпоинте `/api/auth/reset-password` передан валидный токен сброса, но данный токен уже был активирован ранее (`used_at IS NOT NULL`).

### 2.3. 200 OK против 201 Created и 204 No Content
- **`200 OK`**: Стандартный успешный ответ с полезной нагрузкой (Payload) в теле ответа.
- **`201 Created`**: Обязан возвращаться, когда результатом выполнения запроса стало появление нового постоянного ресурса на сервере (задача, пользователь, вложение). В теле возвращается созданный объект с присвоенным первичным ключом.
- **`204 No Content`**: Запрос успешно выполнен, но телу ответа не требуется нести данные (отзыв сессии `DELETE /api/auth/sessions/:id` или выход `POST /api/auth/logout`).

## 3. Централизованный глобальный перехватчик ошибок

В файле [src/server/app.ts](file:///d:/SPP/7sem/SPP/lab3/src/server/app.ts) зарегистрирован терминальный middleware обработки ошибок Express:

```typescript
app.use((err: unknown, req: Request, res: Response, _next: NextFunction) => {
  let errorMessage = 'Внутренняя ошибка сервера';
  let statusCode = 500;
  let errorCode = 'INTERNAL_SERVER_ERROR';

  if (err instanceof multer.MulterError) {
    statusCode = 400;
    errorCode = 'FILE_UPLOAD_ERROR';
    if (err.code === 'LIMIT_FILE_SIZE') {
      errorMessage = 'Файл слишком большой. Максимальный размер: 5 МБ.';
    } else {
      errorMessage = `Ошибка загрузки файла: ${err.message}`;
    }
  } else if (err instanceof Error) {
    errorMessage = err.message;
    statusCode = 400;
    errorCode = 'BAD_REQUEST';
  }

  logger.error('Перехвачена ошибка обработки запроса', {
    requestId: req.id,
    url: req.originalUrl || req.url,
    method: req.method,
    statusCode,
    errorCode,
    error: errorMessage
  });

  res.status(statusCode).json({
    error: errorMessage,
    code: errorCode,
    statusCode
  });
});
```

Это гарантирует:
1. Исключение аварийного падения процесса Node.js при любых исключениях в контроллерах.
2. Автоматическую фиксацию инцидента в структурированном логе с привязкой к `requestId`.
3. Возврат клиенту валидного JSON с понятным текстовым сообщением и точным HTTP-статусом.
