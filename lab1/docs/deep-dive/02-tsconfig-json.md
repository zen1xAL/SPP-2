# Разбор файла [tsconfig.json](file:///d:/SPP/7sem/SPP/tsconfig.json)

Файл `tsconfig.json` указывает компилятору TypeScript (`tsc`), по каким правилам производить статический анализ кода, как проверять типы и в какой диалект JavaScript компилировать исходники.

---

## 1. Построчный анатомический разбор

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "rootDir": "src",
    "outDir": "dist",
```

### Разбор базовых настроек:
* `"target": "ES2022"`:
  * Определяет версию стандарта ECMAScript, в которую компилируется код.
  * `ES2022` поддерживает современные возможности движка V8: классовые поля, метод `Array.prototype.at()`, регулярные выражения с флагом `d`, а также нативный Top-Level Await.
* `"module": "NodeNext"` и `"moduleResolution": "NodeNext"`:
  * **Самая важная и строгая связка настроек для современного Node.js**.
  * Она заставляет TypeScript вести себя в точности так, как ведет себя нативный загрузчик модулей Node.js в режиме ESM.
  * **Почему в импортах TypeScript мы пишем `.js`?** (например, `import { Task } from './task.js';`). Это частый вопрос на защитах:
    * При режиме `NodeNext` TypeScript не подменяет пути импортов во время компиляции. В скомпилированном JavaScript Node.js требует явного указания расширения файла для относительных импортов (`./task.js`). Компилятор TypeScript заранее заставляет нас указывать конечное расширение `.js`, при этом сам проверяет исходный файл `.ts`.
* `"rootDir": "src"`: входная корневая директория с исходным кодом.
* `"outDir": "dist"`: папка, в которую компилятор складывает сгенерированные файлы `.js` и карты исходников.

## 2. Строгий режим проверок (Strict Mode)

```json
    "strict": true,
    "noImplicitAny": true,
    "strictNullChecks": true,
    "strictFunctionTypes": true,
    "noImplicitThis": true,
    "alwaysStrict": true,
```

### Разбор защитных механизмов:
* `"strict": true`:
  * Главный переключатель строгой типизации. Автоматически включает комплексные проверки, делая TypeScript максимально строгим.
* `"noImplicitAny": true`:
  * Запрещает неявный тип `any`. Если TypeScript не может самостоятельно вывести тип переменной или параметра функции из контекста, он выбросит ошибку компиляции и потребует явно объявить тип (например, `value: unknown` или `id: string`).
* `"strictNullChecks": true`:
  * В обычном JavaScript значения `null` и `undefined` могут быть присвоены переменной любого типа (например, числовой или строковой), что приводит к классической ошибке `TypeError: Cannot read properties of undefined`.
  * При `strictNullChecks` значения `null` и `undefined` являются отдельными независимыми типами. Чтобы переменная могла принимать пустое значение, разработчик обязан явно объявить объединение: `string | null`.
* `"strictFunctionTypes": true`:
  * Включает строгую проверку контравариантности параметров функций, предотвращая ошибки при передаче функций с несовместимыми сигнатурами в качестве колбэков.
* `"noImplicitThis": true`:
  * Запрещает обращение к ключевому слову `this` с неявным типом `any`, исключая потерю контекста выполнения.
* `"alwaysStrict": true`:
  * Парсит все файлы проекта в строгом режиме JavaScript (`"use strict"`), запрещая устаревшие опасные конструкции (например, объявление переменных без `let`/`const`).

## 3. Правила чистоты кода и линтинга компилятора

```json
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
```

### Назначение флагов:
* `"noUnusedLocals": true`: компилятор запрещает оставлять объявленные, но неиспользуемые локальные переменные.
* `"noUnusedParameters": true`: запрещает неиспользуемые параметры функций (если параметр необходим сигнатуре, но не используется в теле, его имя по соглашению начинают со знака подчеркивания, например `_req`).
* `"noImplicitReturns": true`: гарантирует, что если функция имеет возвращаемый тип, то абсолютно каждая ветвь выполнения (все `if` и `else`) завершается инструкцией `return`.
* `"noFallthroughCasesInSwitch": true`: защищает от случайного проваливания из одной ветки `case` в другую в конструкциях `switch` из-за пропущенного `break`.
* `"esModuleInterop": true`: обеспечивает прозрачную совместимость между модулями CommonJS и ES Modules.
* `"skipLibCheck": true`: ускоряет компиляцию, пропуская повторную проверку типов внутри сторонних файлов библиотек `.d.ts` в `node_modules`.
* `"forceConsistentCasingInFileNames": true`: гарантирует одинаковый регистр символов в именах файлов при импорте. Это исключает баги, когда на Windows (регистронезависимая файловая система) импорт работает, а на Linux-сервере (регистрозависимая система) падает с ошибкой модуля.

## 4. Границы проекта: `include` и `exclude`

```json
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist", "tests", "uploads", "data"]
}
```
* `"include": ["src/**/*"]` – компилятор обрабатывает строго исходные файлы в папке `src/`.
* `"exclude"` – исключает из сборки папку тестов, зависимости, скомпилированные файлы и локальные папки хранения данных.

## 5. Фундаментальный принцип: Стирание типов (Type Erasure)

Важно понимать, как TypeScript работает на уровне машины:
* Все типы, интерфейсы, дженерики и псевдонимы типов (`type`, `interface`, `<T>`) существуют **исключительно на этапе компиляции**.
* В момент сборки компилятор `tsc` просто стирает все аннотации типов (Type Erasure), оставляя чистый валидный JavaScript.
* Никакой информации о типах TypeScript в оперативной памяти во время выполнения программы (`runtime`) **не остается**. Именно поэтому критически важна валидация данных во время выполнения (User-Defined Type Guards), о которой рассказано в разборе файла доменных моделей.
